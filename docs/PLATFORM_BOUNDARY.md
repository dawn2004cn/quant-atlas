# 主平台与历史脚本边界

## 目的

这份文档用来回答一个最容易让新成员困惑的问题：这个仓库里哪些是当前主平台，哪些是历史脚本或辅助工具。

## 当前主平台

以下内容应视为当前主平台的正式入口与正式代码组织：

- 启动入口：`run.py`
- 主应用包：`app/`
- 运行配置：`app/config.py` 与 `config/`
- 运行时数据：`instance/`
- 正式测试：`tests/`
- 平台文档：`docs/`

日常开发、问题排查、功能扩展，应优先围绕以上目录进行。

## `scripts/` 的定位

`scripts/` 不再视为主应用的一部分，而是混合目录，主要包含三类内容：

1. 历史遗留脚本
   早期原型或旧入口，帮助理解项目演进，但不应继续作为平台架构基准。
2. 运维与迁移工具
   例如数据初始化、缓存处理、数据库迁移、补数、巡检等。
3. 实验性脚本
   包括策略验证、数据抓取尝试、一次性分析与临时测试。

## 团队约定

- 新功能默认落在 `app/` 与 `tests/`，而不是 `scripts/`。
- 新的生产链路脚本需要在文档中声明用途、调用方式和是否仍被调度系统依赖。
- 若某个 `scripts/` 脚本仍是生产必需，应逐步迁入 `app/tasks`、`app/application/services` 或明确的运维目录。
- 文档和讨论中提到“系统入口”时，默认指 `run.py` 与 `app/`。

## 推荐的后续整理方式

- 给 `scripts/` 增加分层子目录，如 `ops/`、`migrations/`、`experiments/`。
- 对仍在使用的脚本建立清单，标注“保留 / 待迁移 / 可归档”状态。
- 在 PR 评审中避免把新业务继续堆进 `scripts/`。
