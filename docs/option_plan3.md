作为资深架构师，在完成了核心依赖注入（DI）和高性能 Rust 计算桥接后，Quant Atlas 已经解决了“连接”和“算力”问题。

  现在，为了让系统具备真正的量化工程规模化能力，我们需要进入架构的深水区。我将针对 app 代码库进行最后一次全局扫描，并提出基于领域逻辑治理的系统级重构计划。

  ---

  一、 全局架构“深层病灶”分析
  当前的架构在 DI 后虽然结构清晰，但在业务逻辑深度上仍存在以下三大短板：

   1. “瘦 Domain，肥 Service” (贫血领域模型)：
       * 表现：StockApplicationService、RiskAlertService 等充当了“大管家”，既管数据获取，又管业务规则（如“斐波那契支撑位”、“主力资金流向判定”）。
       * 风险：业务逻辑被锁死在服务中，无法被回测引擎、AI Agent 或其他模块以纯函数方式复用。
   2. 数据契约隐患 (Type Inconsistency)：
       * 表现：虽然引入了 DI，但函数间传递的 history: list[dict[str, Any]] 依然是“黑盒”。你不知道每一行 dict 里具体有哪些字段，必须依靠 get() 运行时检查，代码极其脆弱。
   3. 横切关注点污染 (Cross-cutting Concerns)：
       * 表现：日志、异常捕获、限流逻辑与业务代码缠绕在一起，降低了代码的核心密度（Signal-to-Noise Ratio）。

  ---

  二、 系统级重构优化计划 (Phase 13-16)

  Phase 13: 领域实体模型化 (Domain Rich Model)
   * 目标：将业务逻辑从 Service 移动到 Domain 模型中。
   * 动作：
       * 定义 app/domain/models/indicator_result.py，使用 Pydantic 定义指标的输入输出约束。
       * 将 RiskAlertService 中的风控判定逻辑封装为 RiskPolicy 实体。
   * 收益：核心规则变更为纯逻辑计算，可直接被回测引擎、实盘引擎、AI Agents 共享，无需任何环境上下文。

  Phase 14: 数据流水线与契约化 (Pipeline & Data Contract)
   * 目标：建立严格的数据流类型契约。
   * 动作：
       * 定义 app/domain/dto/market_data.py。
       * 将所有数据读取接口返回值改为 List[BarData]（BarData 为 TypedDict 或 Pydantic BaseModel）。
   * 收益：彻底杜绝 KeyError 导致的运行时崩溃。

  Phase 15: 装饰器化的切面处理 (AOP)
   * 目标：剥离横切关注点。
   * 动作：
       * 使用 Python 装饰器 (@trace, @monitor_latency, @log_error) 处理日志、监控和限流，保持 Service 方法仅保留 5-10 行核心业务代码。
   * 收益：代码整洁度提升，运维逻辑与业务逻辑彻底解耦。

  Phase 16: 并发与异步升级 (Async Infrastructure)
   * 目标：消除 I/O 阻塞。
   * 动作：
       * 将现有 Service 转为 async 实现，特别是在 TdxSyncService 或 API 路由层。
       * 利用 asyncio 进行并发请求，大幅提升行情数据采集速度。

  四、 下一步实施意图

  为了让你看到最立竿见影的效果，我建议我们先实施 Phase 14 (数据契约标准化)。

  这将通过定义一套“不可逾越”的数据契约（DTO），强制所有模块按照标准结构传递数据。这不仅是重构的终点，更是未来系统健壮性的保障。
