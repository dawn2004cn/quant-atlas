32. 单一职责原则：每个模块、类和函数都应该有一个明确的职责，避免功能混杂，提高代码的可读性和可维护性。
33. 开放封闭原则：系统设计应该对扩展开放，对修改封闭，通过接口和抽象类等方式实现功能的扩展，避免直接修改已有代码，降低风险。
34. 里氏替换原则：子类应该能够替换父类而不影响系统的正确性，确保代码的可替换性和灵活性。
35. 接口隔离原则：设计多个专门的接口，而不是一个单一的总接口，让用户只需要依赖他们感兴趣的接口，减少不必要的依赖，提高系统的灵活性。
36. 依赖倒置原则：高层模块不应该依赖低层模块，二者都应该依赖抽象；抽象不应该依赖细节，细节应该依赖抽象。通过依赖注入等方式实现模块之间的解耦，提高系统的可维护性和可扩展性。

23种设计模式的合理运用：如工厂模式、单例模式、观察者模式、策略模式等，根据具体功能需求选择合适的设计模式，提升系统的灵活性和可维护性。
1. 单例模式：对于系统中需要全局唯一实例的模块，如配置管理器、日志记录器等，采用单例模式确保只有一个实例存在，避免资源浪费和数据不一致。
2. 工厂模式：对于需要创建复杂对象的模块，采用工厂模式封装对象的创建过程，提供统一的接口，简化代码并提高可维护性。
3. 观察者模式：对于需要实现事件驱动的模块，采用观察者模式实现模块之间的通信和数据更新，确保系统的响应性和灵活性。
5. 策略模式：对于需要根据不同条件选择不同算法的模块，采用策略模式封装算法的实现，提供统一的接口，简化代码并提高可维护性。
6. 适配器模式：对于需要兼容不同接口的模块，采用适配器模式实现接口的转换，确保系统的兼容性和灵活性。
7. 装饰器模式：对于需要动态添加功能的模块，采用装饰器模式实现功能的扩展，避免修改原有代码，提高系统的灵活性和可维护性。
8. 代理模式：对于需要控制访问的模块，采用代理模式实现对对象的访问控制，增强系统的安全性和灵活性。
9. 迭代器模式：对于需要遍历复杂数据结构的模块，采用迭代器模式提供统一的接口，简化代码并提高可维护性。
10. 组合模式：对于需要表示树形结构的模块，采用组合模式实现对象的组合和层次结构，提供统一的接口，简化代码并提高可维护性。
11. 命令模式：对于需要将请求封装为对象的模块，采用命令模式实现请求的参数化和队列化，提供统一的接口，简化代码并提高可维护性。
12. 责任链模式：对于需要处理请求的模块，采用责任链模式实现请求的传递和处理，增强系统的灵活性和可维护性。
13. 状态模式：对于需要根据对象状态改变行为的模块，采用状态模式实现状态的封装和行为的改变，增强系统的灵活性和可维护性。
14. 备忘录模式：对于需要保存对象状态的模块，采用备忘录模式实现对象状态的保存和恢复，增强系统的灵活性和可维护性。
15. 访问者模式：对于需要在不修改对象结构的情况下添加新功能的模块，采用访问者模式实现功能的扩展，增强系统的灵活性和可维护性。
16. 桥接模式：对于需要将抽象部分与实现部分分离的模块，采用桥接模式实现抽象和实现的解耦，增强系统的灵活性和可维护性。
17. 享元模式：对于需要大量创建相似对象的模块，采用享元模式实现对象的共享和复用，减少内存消耗，提高系统的性能。
18. 中介者模式：对于需要协调多个对象交互的模块，采用中介者模式实现对象之间的通信和协调，增强系统的灵活性和可维护性。

MVP Python 项目设计规范、代码要求与重构要求

1. MVP 整体设计原则
MVP 核心目标：快速验证假设，用最小成本交付可用的核心功能。
设计原则（优先级顺序）：

YAGNI（You Aren't Gonna Need It）：只实现当前必须的功能，拒绝“未来可能有用”的功能。
KISS（Keep It Simple, Stupid）：优先简单方案。
迭代优先：代码必须易于快速迭代和重构。
可观测性：日志、错误追踪、核心指标必须先行。
可维护性 > 完美性能/架构（MVP 阶段）。

3. 代码要求（强制）
3.1 编码规范

严格遵守 PEP 8 + ruff 检查。
单行最大长度 100（推荐 88）。
使用 Black 格式化 + isort 排序。
类型提示 必须（Python 3.10+），复杂函数必须完整标注。

3.2 命名规范

变量/函数/方法：snake_case
类：PascalCase
常量：UPPER_CASE
私有： _single_leading_underscore
避免缩写，除非是行业公认（如 db, id, uuid）

3.3 模块与依赖

每个文件不超过 300 行（强烈建议 < 200 行）。
单个函数/方法不超过 50 行（复杂逻辑必须拆分）。
避免循环导入。
使用 pyproject.toml + poetry 或 uv 管理依赖（推荐）。

3.4 错误处理

不要裸 except:
自定义业务异常继承 Exception 或 ValueError
使用 loguru 或 structlog 记录错误（带上下文）
API 层统一使用异常处理器返回标准格式

3.5 日志与可观测性

重要路径必须打日志（INFO/WARNING/ERROR）
使用结构化日志
记录请求耗时、关键业务事件、错误栈

3.6 安全性基础要求

所有外部输入必须验证（Pydantic v2）
敏感信息不打印、不记录日志
使用 secrets 生成 token 等
依赖及时更新（dependabot 或手动检查）


4. 架构设计要求（MVP 适用）

推荐分层（由外到内）：API → Service → Repository → Model
业务逻辑尽量放在 Service 层
复杂领域逻辑推荐使用领域模型（Rich Domain Model）
数据库访问统一走 Repository 模式（便于后续切换或 mock）
异步优先（FastAPI + async SQLAlchemy / Tortoise / Piccolo）

MVP 允许的妥协：

可以先把逻辑全写在 API 层，验证通过后再重构到 Service。
可以先用 SQLite，验证后再换 PostgreSQL。


5. 重构要求（非常重要）
5.1 何时必须重构

代码重复超过 3 次（DRY 原则）
函数/类超过 100 行
一个文件超过 350 行
出现 God Class（一个类承担过多职责）
测试覆盖率低且难以测试的代码
核心路径性能明显影响用户体验

5.2 重构原则

小步重构：每次只改一点，保持功能不变。
先写测试（如果没有）：重构前必须有测试保护。
重构后跑全量测试。
不要在重构中加新功能。
核心业务模块重构前必须 Code Review。

5.3 重构优先级（MVP 阶段）

高：bug 频发区域、核心交易/计费/用户数据路径
中：重复代码、难以理解的逻辑
低：边缘功能、后台管理


6. 测试要求

核心业务逻辑必须有单元测试
API 接口建议有集成测试
至少覆盖 80% 的核心路径
使用 pytest + pytest-asyncio

量化平台典型架构层次1. 数据采集与预处理层 (Data Acquisition Layer)职责：从外部交易所API（如Binance, OKX）、金融数据服务商（如Tushare, Wind）获取实时或历史数据。功能：数据清洗、数据对齐、异常值处理、数据格式化。2. 存储层 (Storage/Persistence Layer)职责：持久化存储采集到的数据和系统状态。功能：关系型数据库 (MySQL/PostgreSQL)：存储用户信息、配置、策略参数、交易订单记录。时间序列数据库 (InfluxDB/TimescaleDB)：存储高频K线、Tick数据、因子数据（擅长时序查询）。缓存 (Redis)：存储实时行情、高频热数据、分布式锁。3. 领域服务层 (Domain Service Layer)职责：核心业务逻辑封装，处于 Flask 应用的核心。功能：策略执行引擎：运行交易策略。回测引擎：基于历史数据进行策略仿真。风险控制模块：校验下单的仓位、保证金、最大持仓等风险指标。4. 接口服务层 (Service/API Layer - Flask)职责：提供 RESTful API 或 WebSocket 接口，连接外部和前端。功能：Flask 视图函数 (Views)、请求处理、数据验证、与服务层交互、管理认证。5. 接入层与展示层 (Presentation/Client Layer)职责：前端页面或自动化交易接口。功能：前端界面展示数据、策略监控、手动下单界面，或对接量化客户端。
