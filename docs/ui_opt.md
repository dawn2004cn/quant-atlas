在以用户为中心的视角下，检查当前的 app/presentation（页面与路由链路），Quant Atlas 展现出非常专业的工程能力，但在“从数据到决策”的认知闭环上存在明显的割裂。

  我们将链路简化为：数据同步 -> 研报预览 -> 策略分析 -> 交易下单。以下是针对该链路的三个维度的优化建议：

  ---

  一、 核心链路优化：从“堆砌信息”到“引导决策”

  1. 研报/快讯的“提炼链路” (Research-to-Insight Path)
   * 当前链路：用户在 /market/headlines 或 /stock-news 中看到杂乱的新闻流。
   * 优化建议：引入“信号标注 (Signal Tagging)”。
       * 实践：不需要用户点开每条新闻，在后端（基于 FinGPT）对头条自动加标注：[利好/利空/中性]、[影响板块/标的]、[情绪评分]。在前端以“气泡标签”呈现。
       * 用户价值：将 5 分钟的阅读时间压缩至 10 秒的快速筛选。

  2. 策略分析的“对比链路” (Comparison Path)
   * 当前链路：查看 /stocks/<symbol>/analysis，只能看到当前标的的数据。
   * 优化建议：“对标 (Benchmarking) 链路”。在分析页增加一个简单的“对比框”，允许用户输入一个同行业标的，通过 AttributionReportDTO 对比两个标的在因子暴露度（Factor
     Exposure）上的异同。
   * 用户价值：消除“个股孤岛”，提供更客观的仓位对比建议。

  3. 交易下单的“确认链路” (Order-Confirmation Path)
   * 当前链路：下单是一个独立的功能点，与分析逻辑分离。
   * 优化建议：“交易建议融合”。当用户在策略建议页 (/strategy/copilot) 点击某策略时，直接通过弹窗展示该策略的“风控评分”。如果不符合 PreTradeValidator
     的门禁，直接在页面报错，而不是在下单接口调用时才报错。
   * 用户价值：实现“防呆”，减少无效下单的心理挫败感。

  ---

  二、 页面交互的“心智模型”优化 (Mental Model Optimization)

  4. 每日工作台的“焦点管理” (Focus Management)
   * 现象：DailyWorkbenchService 负责汇总数据，但页面可能展示了过多的信息。
   * 优化建议：“晨会模式 (Morning Call Mode)”。增加一个全局看板模式，按“今日风险、今日机会、系统健康”三个维度进行自动轮播。
   * 用户价值：减轻交易员早晨开盘前的焦虑，优先处理最要紧的事情。

  5. 错误提示的“可操作性” (Actionable Errors)
   * 现象：当前的 API 报错往往是 ValidationError 或通用 500。
   * 优化建议：在 app/presentation/api/error_handlers.py 中引入“修复建议”。比如，“数据未同步”的错误，提示不仅仅是“错误”，还应附上“触发一次手动同步的按钮”。
   * 用户价值：把“报错”变成“操作向导”。

  ---

  三、 总结：用户中心的三个“关键词”

  如果你想优化现在的页面链路，只需紧扣这三个词：

   1. 缩短（Shorten）：从新闻 -> 研报 -> 交易，能否在研报里直接看到交易建议？
   2. 可视化（Visualize）：因子暴露度是否能用雷达图表示，而不是枯燥的表格？
   3. 信任（Trust）：每一步分析结论，能否附带一个“置信度（Confidence Score）”？

  Quant Atlas 的页面链路目前是“全功能型”的，但在“交互流”上倾向于程序员思维。如果你是为普通交易员或策略研究员准备的平台，现在的链路稍显厚重。

  建议下一步：
  先从 “单页面决策看板 (Decision Dashboard)” 入手，将目前的各个 API 端点串联到一个聚合页面中。

  针对你目前现有的 app/presentation 层，你需要我为您挑选一个“重灾区”（即逻辑最复杂但用户最常用的页面）进行深度剖析吗？
  

我们将视角从“功能链路”下沉到“交互反馈与心理模型”。一个优秀的量化平台不仅要提供数据，更要帮助用户降低认知负荷（Cognitive Load）。

  Quant Atlas 目前在页面链路设计上还存在三个“交互鸿沟”，这些鸿沟正在无意中增加用户的心理损耗：

  1. 响应鸿沟 (The Feedback Gap)：请求的“透明化”
   * 痛点：在进行因子挖掘或数据刷新（market/basic-data/refresh）时，系统要么走异步队列（返回 task_id），要么同步等待，用户界面通常处于“静默”或“转圈”状态。
   * 优化实践：
       * WebSocket 推送：不要让用户去轮询 /system/celery/inspect。当后台任务完成时，后端应通过 WebSocket 实时推送 TaskSucceeded 事件，界面自动更新。
       * 进度预估：针对耗时任务（如大数据量回测），后端应在 Pipeline 运行中提供 Heartbeat 信号，更新处理进度（如“正在处理第 15/100 组标的”），消除用户的焦虑感。

  2. 决策鸿沟 (The Semantic Gap)：上下文的“一致性”
   * 痛点：从 行情看板 -> 研报列表 -> 策略分析 的跳转过程中，上下文标的（Symbol）经常丢失。用户被迫在不同页面重复输入相同的股票代码。
   * 优化实践：
       * 全局上下文路由：将标的（Symbol）和市场（Market）信息通过 URL 状态（?symbol=000001&market=CN）进行持久化。
       * 单点聚焦组件：在页面顶部设计一个通用的“焦点栏 (Focus Bar)”，用户修改焦点栏的标的，下方所有模块（行情、新闻、分析、风控）自动同步刷新。
   * 用户价值：实现“心流”研发，用户不再需要频繁切换输入焦点。

  3. 系统健康度鸿沟 (The Trust Gap)：防御性 UI
   * 痛点：系统出现异常时，页面经常返回 500 或空白。对于量化系统，“不知道系统坏了”比“系统坏了”更可怕。
   * 优化实践：
       * 状态指示器：在 UI 的角落加入一个“系统健康指示灯”，绑定你目前的 DataFreshnessSentinel 和 CircuitBreaker
         状态。如果行情源断开，灯变为红色，并在页面顶部显眼位置提示：“当前行情延迟 X 分钟，不建议执行实盘交易”。
       * 预期管理：在策略分析页，增加一个“数据覆盖度”指标。如果某标的缺失了最近几天的 K 线，在分析结论旁边显眼处标注：“本结论基于缺失数据，置信度低”。

  四、 从架构层面的“降维打击”：以用户为中心的重构优先级

  如果要优化前端链路，建议按照用户感受到的“控制感”优先级来排期：

   1. Level 1（控制感）：将 “决策证据” (Decision Evidence) 放在决策结果的旁边（即 Phase 46 的延伸）。当策略推荐一个买入点时，立即显示当时触发的因子值。这是用户最在乎的。
   2. Level 2（连贯性）：实现 “全局标的追踪”。确保 URL 路由逻辑能覆盖所有功能区，让用户可以通过发送 URL 分享策略分析视图。
   3. Level 3（自愈性）：将所有的 API 错误封装为 “业务错误”，前端界面直接渲染错误原因，并附带修复操作引导。

  一、 交互逻辑的“认知减负”优化

  1. 策略分析链路：从“数据展示”到“假设验证”
   * 不合理之处：当前的策略分析页面是一个纯粹的“指标仪表盘”（Build Analysis -> Display），用户看完结论后，依然要自己大脑构建买卖逻辑。
   * 优化实践：“假设-结论（Hypothesis-Based）”链式交互。
       * 在分析接口中引入一个 user_hypothesis 参数。用户点击“分析”前，先选择一个假设（如：“我认为该股在反弹，但量能不足”）。
       * 后端分析引擎基于该假设，返回的 DTO 中不仅有指标，还有针对该假设的“反驳/佐证”证据。
   * 用户价值：用户不再是被动阅读数据的消费者，而是与 AI 分析师协作的观察者。

  2. 数据读取链路：从“全量查询”到“智能采样” (Smart Sampling)
   * 不合理之处：stock_history 接口通常直接返回整个时间段的数据。用户在前端渲染时，往往不得不自己进行降采样或数据压缩。
   * 优化实践：服务端自适应采样。stock_history 接口根据前端的容器宽度（如页面只有 1000px）自动应用 LTTB (Largest-Triangle-Three-Buckets) 采样算法，只返回视觉上最重要的关键点。
   * 用户价值：页面加载从秒级提速到毫秒级，且前端渲染压力大幅降低，响应更灵敏。

  3. 异步任务链路：从“等待结果”到“进度预告”
   * 不合理之处：在执行大规模任务时，前端除了进度条，没有任何交互反馈。
   * 优化实践：分层反馈链路。
       * dispatch 任务时，不仅返回任务 ID，同时返回一个“预计处理路径”（如：{"estimated_steps": ["数据清洗", "指标计算", "策略触发", "持久化"]}）。
       * 前端根据这些步骤实时点亮进度条。
   * 用户价值：用户能够感知系统正在“干活”，而不是“死机了”。

  二、 一个关键的架构隐患：数据“语义隔离”的缺失

  在你的系统链路中，有一个非常容易引发 User 投诉的功能点：研报与行情数据的时序对齐。

   * 隐患：你在后台拉取研报，又在本地缓存行情。当用户看某只股票历史走势时，研报的标注点往往因为“时间戳对齐”微小的误差（如秒级与日级），导致标注飘移到错误的 K 线位置。
   * 架构优化建议 (建议记录在 MEMORY.md)：
       * 建立一个 “对齐层 (Alignment Layer)”，所有的研报、重大新闻、策略交易信号，都必须通过 SymbolNormalizer 和 DateAligner 强制对齐到统一的市场时钟。
       * 在 DTO 设计中，增加 market_time_slot 字段，确保所有数据在 UI 展示前已经过“强制同步”。

   2. 链路的“闭环化”：在分析页面的任何一个结论旁边，都应该有一个“追踪”按钮，点击后立即跳转到触发该结论的最原始数据行。
