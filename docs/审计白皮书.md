   一、多角色交叉现状审计报告 (The Raw Truth)

   1.1 界面与交互审计（交易员 × 前端 × 产品）

   信息密度与视觉层级

   致命问题：没有统一的交易入口。

   - 不存在独立的订单Ticket组件。交易UI被拆成三块：Professional Workbench 的机构执行算法（professional_workbench.html:116-156）、React SPA 的
   TradePlanPanel.tsx（只读建议面板）、Signal Observations 的模拟观察单（signal_flag.html:44）。
   - 用户从"看到信号"到"实际下单"需要跨越至少 2-3 个不同页面，且没有一键下单路径。
   - 移动端虽然加了 qc-mobile-lane 和 navToggleBtn（base.html:185-216、base_app.js:360-376），但没有独立的移动下单表单；在 640px
   以下宽屏，专业版网格会退化为单列（professional_workbench.html:21），但交易按钮是否仍然可见取决于具体断点，存在操作盲区。

   渲染性能

   K线采用 TradingView Lightweight Charts，但上层架构拖后腿。

   - K线主引擎是 lightweight-charts.standalone.production.js，stock_detail.html:636 本地加载，chart_service.js:60-121 做了一层封装。 Lightweight Charts 本身足够 60fps@10K bars。
   - 问题是：同一个系统里并存三套图表栈——LightweightCharts（K线）、ECharts（研究雷达图）、Recharts（React SPA 曲线图）。三套栈各自加载 JS bundle，首屏体积失控。
   - 交易信号页（ai_analysis.html:186-403）直接把因子暴露表、base_alpha、peer_alpha 作为 DOM 行内渲染，长列表没有虚拟滚动证据。
   - 状态管理使用自定义 QCStateBus（static/js/state_bus.js）+ Alpine.js + React useState/useSWR，没有统一的数据 diff 机制。高频 tick
   进来后是否触发全页重渲染，取决于每个页面自己的监听实现，无法保证。
   - WebSocket 消息在 base_app.js:453-486 转成 CustomEvent，任何订阅 quant:quote 的组件都会收到广播，缺少按 symbol 细分的订阅过滤。

   移动端适配

   - base.html:6-7 显式关闭了 mobile-web-app-capable，说明当前未按 PWA 设计。
   - 30+ 模板内联 @media 查询，没有统一设计系统，维护成本高，不同页面断点不一致（900px、768px、640px、600px 混用）。

   量化策略模块

   回测引擎多达 5 个，结果不可互信的。

   - Legacy BacktestEngine（app/infrastructure/providers/backtest_engine.py）逐行循环，正确切片到 i+1 避免前视偏差，但止盈未实现。
   - FastBacktestEngine（app/modules/strategy/services/strategy/fast_backtest_engine.py）是"快速预览"引擎： Lake 没数据时用 np.random.seed(42)
   生成合成数据（fast_backtest_engine.py:42-54），收益公式是 returns + (param_factor * 0.001)（fast_backtest_engine.py:107）——这不是策略信号，是伪造曲线。
   - CompositeEngine 系列（app/infrastructure/agent/backtest/engines/）按市场分 A股/港股美股/期货/加密/外汇，信号 shift(1) 实现 next-bar-open，是五套引擎里最严谨的生产引擎。
   - VectorizedBacktestService（app/modules/strategy/services/boutique_tier_service.py:41-140）走 NumPy/Polars 全向量化路径。
   - Domain model BacktestEngine（app/domain/models/backtest_models.py:70-110）直接硬编码 max_drawdown=0.05、sharpe_ratio=0.5（backtest_models.py:108-109），是 stub。

   问题本质：不同场景调用不同引擎，但用户看到的"回测收益率"可能来自完全不同的计算口径。

   数据精度与因子计算

   - 因子计算既有向量化路径（factor_service.py 用 np.corrcoef，factor.py 用 pandas rolling + shift(1)），也存在 Polars（app/infrastructure/compute/polars_compute.py）和
   Rust-PyO3（app/infrastructure/compute/native_compute.py）高性能路径。
   - 但 FastBacktestEngine 和 Wizard 的快速预览会误导用户：当 Data Lake 无数据时自动 fallback 到合成随机数据，且只在日志里警告（fast_backtest_engine.py:46），UI
   上可能仍然显示为"策略表现"。
   - 没有幸存者偏差控制。回测引擎运行什么 codes 列表由调用方决定；如果调用方传入当前上市股票，结果就是幸存者偏差。
   - 没有真正的 Level-2 数据。tick_stream_service.py:80 用 spread = max(price * 0.0001, 0.01) 合成买卖盘，不是交易所 tick-by-tick feed。

   策略保密性

   - 策略代码通过 importlib 从文件路径动态加载并执行（app/domain/strategies/plugin/loader.py:68-75、app/infrastructure/agent/backtest/runner.py:106-120）。
   - 前端 static/js/alpha_whisper.js、static/js/components/AiResearchReport.js、agent_center.html:315-424 直接把策略类型、因子暴露、回测参数暴露在客户端 JS/HTML 中。
   - 策略代码不在服务端沙箱执行，也不对客户端隐藏。

   1.4 底层架构审计（架构师视角）

   架构模式

   - 模式：模块化单体（Modular Monolith）。14 个 ContextModule 通过注册表发现，但仍在同一个 Flask WSGI 进程内运行。
   - 进程模型：Flask 3.x 同步 WSGI + 独立 ws_gateway 进程（端口 5001）通过 Redis Pub/Sub 桥接 WebSocket。
   - 单点故障：EventBus 是内存单例（app/core/event_bus.py:445-554），服务重启即丢失所有订阅关系；WS Gateway 独立进程崩溃则实时推送全断。

   行情数据管线
    交易所/第三方 → pytdx/Tencent/AkShare/yfinance → MarketDataProvider
                                                   ↓
                                Redis Streams / Redis Pub/Sub / SQLite StockCache
                                                   ↓
                       ws_gateway (Socket.IO 进程) → 浏览器 / React SPA
   - 实时层有 SmartDegradeGateway（app/infrastructure/realtime/smart_degrade_gateway.py）根据 Redis 延迟在 STREAM/BATCH/DEGRADED 之间切换，设计方向正确。
   - 但行情从采集到客户端经过了 Flask HTTP → Redis PUBLISH → WS Gateway → SocketIO → Browser，链路环节过多，端到端延迟无法保证在毫秒级。
   - tick_stream_service.py 是 1 秒轮询 get_realtime_quotes()，不是事件驱动。

   数据层

   - 同时维护三套数据库连接：同步 MySQL（pymysql + scoped_session）、异步 MySQL（asyncmy）、PostgreSQL/TimescaleDB（psycopg）。
   - RepositoryRegistry 工厂（app/infrastructure/repositories/common/factory.py）虽然抽象了 MySQL/SQLite/Postgres，但同一个项目内存在同步和异步两种 Repository
   Base，调用链混用风险高。
   - Redis 使用 RedisClientPool 单例（app/infrastructure/redis_client.py），配置合理（50 连接、3s 连接超时、30s health check）。
   - 内存缓存有 MemoryCache（app/infrastructure/memory_cache.py）统一实现，但历史遗留 CacheService、HotPathCache、RequestCache 等路径仍可能存在。

   鉴权模型

   - Web 页面使用 Flask-Login session cookie；API 使用 @api_auth_required，支持 session 或 Bearer JWT。
   - 缺陷：JWT refresh rotation、token 吊销列表未在代码中体现；admin 路由无角色校验；WebSocket 认证仅在 connect 时一次性校验。

   三、愿景与重构战略 (CEO & 架构师联合蓝图)

   3.1 一句话裁决

   当前 Quant-Atlas 不是生产级付费零售交易平台。它更像一个功能丰富的量化研究与策略原型系统：后端有正确的市场规则抽象（CompositeEngine、ATR
   风控、印花税历史调整），但交易闭环断裂、安全基线缺失、回测口径混乱、实盘规则校验缺位。在让真实资金入场之前，必须完成 P0/P1 安全与交易链路的重构。

   3.3 重构路线图

   Phase 1（0–4 周）：止血（P0 必须修复）

   - 移除 .env 中的真实密码，接入 Vault/KMS；轮换所有已泄露密钥。
   - 给 pages_admin.py 加 @role_required("admin")。
   - 给策略插件 loader 加沙箱执行（RestrictedPython / Docker / gVisor），禁止直接 exec_module。
   - 统一订单生命周期：在 OrderManager 前置 T+1、涨跌停、头寸限制校验。
