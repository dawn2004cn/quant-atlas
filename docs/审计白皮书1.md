一、多角色交叉现状审计报告 (The Raw Truth)

1. 界面与交互审计（交易员 & 前端 & 产品视角）

交易体验断层的核心事实：没有 K 线图

当前所谓的"K-line"图表位于 frontend/src/components/charts/PriceHistoryChart.tsx，实际上只是一个 Recharts <Line> 折线图（第 52-59 行），并非 OHLC 蜡烛图。对于一个量化交易平台，这是一个致命的功能缺失。用户无法看到每日开高低收、无法识别形态、无法做技术分析。recharts 本身不原生支持蜡烛图，且其 SVG 渲染模式在超过 500 根柱子时就会掉帧。

大列表无虚拟化——800 行 DOM 裸渲染

frontend/src/pages/SignalFlag.tsx 第 46-48 行加载最多 800 条记录，第 123 行直接 .map() 渲染为 <tbody>。而 react-window v2.2.7 已在 package.json 第 21 行安装但 从未被使用。前端工程师犯了一个经典错误：装了库但不接入。

SPA 体验被 window.location.href 破坏

SignalFlag.tsx 第 124 行使用 window.location.href = /stock/${code} 进行页面跳转，这会产生完整的浏览器页面重载，丢失所有 React 状态。正确的做法是使用 useNavigate() 或 <Link>。

无 Error Boundary

App.tsx 没有包裹 ErrorBoundary。任何一个未捕获的异常都会导致整个 SPA 白屏崩溃。

JWT 存储在 localStorage——XSS 靶子

frontend/src/api/api.ts 第 36 行将 qa_access_token 写入 localStorage。一旦有任何 XSS 注入，攻击者可窃取所有会话令牌。

Recharts 懒加载块 408 KB

尽管懒加载策略正确，ComposedChart-D_hl0SBt.js 仍是最大的 JS 资源。低频使 线图，用户体验不佳。

CSS 输出 98 KB——DaisyUI 主题膨胀

Tailwind + DaisyUI 编译后的 CSS 达 98 KB，主要来自 DaisyUI 的 5 个主题变量。

2. 功能与业务逻辑审计（交易员 & Quant & 产品视角）

无真实回测可视化

frontend/src/pages/Backtest.tsx 的回测结果仅在 ExperimentReport.tsx 中以手绘 SVG polyline 展示。没有夏普率/最大回撤/年化收益率的数值面板。

因子管理缺少在线计算能力

尽管存在 app/domain/alpha/ 目录（20+ 因子算法），但这些因子 没有通过 API 开放给前端。因子管理页面 frontend/src/pages/AlphaFactory.tsx 只能查看记录，不能在线触发因子计算。

策略保密性风险

策略代码以 Python 明文文件存储在 app/modules/strategy/strategies/，没有混淆、没有加密。任何能访问服务器的内部人员都能完整复制所有策略逻辑。

策略参数字段未做全面校验

app/application/dto/market_data_dto.py:68-75 的 BacktestRequestDTO 只校验了 symbol 和 initial_capital 的边界，但参数组合的合法性（如 MA 策略不需要 RSI 参数）没有校验。

A 股交易规则未在系统层面体现

- T+1 限制：代码库中未有系统级 T+1 结算检查
- 涨跌停限制：app/modules/execution/services/pre_trade_validator.py 中有 于回测场景，未对模拟盘做限制
- Level-2 行情：没有对 Level-2 十档行情的处理管道

4. 底层架构审计（架构师视角）

架构模式：松散的 MVC 拼装体

当前架构是 Flask MVC + 受 DDD 启发的分层 的混合体：
- app/presentation/ — 路由层（MVC Controller）
- app/modules/*/services/ — 服务层（MVC Model，但也是 Application Service）
- app/domain/ — 领域层（DDD Entity + Port）
- app/infrastructure/ — 基础设施
- app/bootstrap_components/ — DI 容器

问题：架构有分层之名，无分层之实

Phase 4/8 的 Layer Compliance 修复（我们刚做完的）只解决了 5 个文件的问题。实际代码库中还有：
- app/application/workflows/* — 8 个文件直接 import app.infrastructure.capabilities.registry
- app/modules/*/services/ — 37 个文件有基础设施直接导入
- app/modules/system/services/tools/tool_facade_service.py 第 14 行直接导入 CapabilityRegistry 从 infrastructure

行情推送架构：WebSocket + SSE 双轨但未做高可用

- frontend/src/hooks/useRealtime.ts — Socket.IO 客户端，只监听一个命名空间
- app/bootstrap_components/realtime.py — Socket.IO 服务端，支持 quote_upd
- app/modules/market_data/services/tick_stream_service.py — 行情感知层

但在高并发下：Socket.IO 在处理 100+ 同时订阅者时，Blocking 模式会导致行情推送 IO 阻塞。

数据一致性：缺少分布式事务保障

mysql_client.py 绕过连接池创建直接连接，可能导致写冲突。没有事务 ID 跟踪，没有两阶段提交。如果 MySQL 和 Redis 同时写入但一个失败，系统进入不一致状态。

缓存架构：多级缓存但缺少自动失效

我们在 Phase 4.2 刚添加了事件驱动的缓存失效机制，但这是全新的——在此之前失ate_prefix()。
